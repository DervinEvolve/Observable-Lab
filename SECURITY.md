# Security reports

Please report Observable-Lab vulnerabilities privately to this repository's maintainer.

If GitHub offers **Report a vulnerability** in this repository's Security tab, use that form. If it is unavailable, ask the maintainer for a private contact route without including the vulnerability, credentials, or exploit details in a public issue.

This is an experimental project. There is no promised response time or supported production security boundary.

Never include provider credentials, database URLs, runner tokens, or private experiment content in an issue, screenshot, or pull request. Revoke exposed credentials through the relevant provider; removing a file from the latest commit does not remove it from Git history.

## Model proposals are never merged automatically

When `LAB_ENABLE_LAB_PROPOSALS` is on, a model may propose a change to this repository. The lab opens it as a pull request labelled `model-proposal` and stops there. There is no merge call in that code path, and its token (`LAB_PROPOSALS_GITHUB_TOKEN`) is a separate fine-grained token for this one repository with Pull requests and Contents permissions only, so it cannot change repository settings, workflow files, secrets or other repositories. The lab only ever writes to `model-proposal/...` branches with it; protect the default branch so that a merge always needs the owner, whatever the token could do.

Only the owner merges these, by hand, because this repository is not like AI-Agent:

- **It deploys to production.** A merge to the deployed branch becomes the live site and API on the next deployment, with no CI gate in between that could judge whether generated code is safe.
- **Its server holds the lab's credentials.** The API functions run with the OpenRouter key, the database URL, the GitHub tokens, the Sprites token, the Modal tokens and the operator and cron secrets. Code merged here runs next to all of them, so a single bad or manipulated proposal could leak them or spend without limit.
- **It is the lab's own control surface.** It decides what the models can do, the spending cap, what the room shows as evidence and what counts as tested. A model must not be able to change those rules for itself.

AI-Agent contributions and exhibits can merge on their own because that repository holds no credentials, deploys nothing, and its changes are limited to source, tests, docs and exhibit data, behind its own required CI checks.

Treat a `model-proposal` pull request as untrusted outside input: read the whole diff, and do not run it with real credentials before you have.

## Conversations visitors offer

When `LAB_ENABLE_VISITOR_OFFERS` is on, a visitor can offer a chat with a trained model to the lab, and only then is that conversation stored (text, the model, and the UTC day; no address, browser string or account). Each reply the chat gives carries a receipt, an HMAC-SHA-256 over the adapter, the day and the conversation so far, so an offer can only hold replies the lab's own endpoint gave, in order. The receipt key is derived from `LAB_OPERATOR_SECRET`, or from `CRON_SECRET` when that is not set, and from nothing else: a leaked database URL cannot forge a receipt, and with neither secret set at 32 characters or more offers are off. Treat those two secrets as the key to that proof. A receipt is a keyed hash a visitor holds, so a guess of the secret can be tested against one receipt without asking the server: the secret has to be long and random. The take back code is shown once and only its hash is stored. Offered text is never public. It is read only through `POST /api/experiment/visitor-offers` with the operator secret (`LAB_OPERATOR_SECRET` itself; with only `CRON_SECRET` set the route answers 503 and nothing can be read or deleted through it), each read is counted in the public record, and no model reads it. The automatic checks refuse emails, long numbers, links and user names, can miss some, and do not find other private details or abuse. An offer row holds no size column and no time of day, and its hashes of the text are overwritten when the text is taken back, deleted or expired. That does not make an offer unlinkable. What can still be joined, by someone who holds the database, on any day: the stored text gives the turns and characters before its last reply, which are the numbers on the chat's own row of counts for that reply (`trained_chat_calls`, kept 30 days with its time), so the time of an offer can be found; and Postgres numbers its transactions, so the row order puts an offer directly after the two rate rows written for its sender (keyed hashes of the address and of the address with the browser string, kept 48 hours, with their own time), which names the sender's hashes. The hashes can be listed with the database alone; the server secret is needed only to test a candidate address against a hash. The public counts also change at the moment of an offer. docs/TOOLS.md, "What can still be joined", has the detail and what ending it would take. An offer past its expiry is not read, claimed or counted even before the hourly tick clears its text, and that tick vacuums the table so deleted text leaves the table file within the hour; the database provider's own history (write ahead log, point in time restore) can still hold it for as long as the provider keeps it. A training run on offers keeps none of the runner's free text: a fixed reason for a failure, a fixed sentence for an export error, and an early stop note only when it is one of the runner's own limit sentences. Please report anything that lets a visitor read, forge or delete another person's offer, or reach the text without the operator secret, privately as described above.
