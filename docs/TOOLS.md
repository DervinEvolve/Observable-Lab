# The tool menu

In a classic epoch the Executor may return an optional `tools` object next to its proposal. It chooses from what is switched on for this deployment, and the prompts list exactly those tools, generated from the same configuration the server uses (`api/_lib/tools-config.ts`, `api/_lib/prompts.ts`). A tool that is off is not mentioned to the models at all.

**Every tool is off unless its flag is `true` and what it needs is configured.** Each has a per-epoch limit (fixed) and a per-day limit (UTC, configurable), and everything a tool costs counts against `LAB_DAILY_BUDGET_USD`. Unknown or switched-off tools, malformed requests and requests over a limit are ignored, logged and stored as `skipped`; they never crash the epoch. A resumed epoch never runs a tool twice.

| `subagents` | `LAB_ENABLE_CODE_WRITES=true` | the contribution setup | 0 to 2 explorers and 0 or 1 test subagent | `LAB_SUBAGENTS_PER_DAY` (24) |
| `sprite_session` | `LAB_ENABLE_SPRITE_SESSIONS=true` | `SPRITES_TOKEN` | 1 session, up to 4 commands | `LAB_SPRITE_SESSIONS_PER_DAY` (8) |

Web search is not on this menu: the Planner and Executor calls, and the explorer subagents, already use OpenRouter's web plugin, as before.

## When each runs

- **Side tools** (`sprite_session`, `gpu_job`, `weights`) start as soon as the Executor has answered and run while the Challenger, the rebuttal and the Reviewer talk. The runner waits for them before the Commentator, who is given a one-line summary of each, built from the stored records. Weights asked for are fetched before that epoch's GPU job starts. A request for a [public dataset](#public-datasets) (`datasets`) is a side tool too, and is fetched before a GPU job that names it.
- **Subagents** are part of the epoch's one code contribution, after the Reviewer.
- **Deliverables** (`exhibit`, `lab_proposal`, `tinker_train`, `keep_adapter`) run after the Reviewer, alongside the code contribution, and only when the Reviewer answered `"tool_verdicts": { "exhibit": "approve" }`, `{ "lab_proposal": "approve" }`, `{ "tinker_train": "approve" }` or `{ "keep_adapter": "approve" }`. Anything else is a no. A Tinker training run, or the keeping of an adapter, can outlast the follow-up that starts it; a later tick collects its result.
- The recent runs (not the skipped ones) go into the next epoch's shared context as `RECENT TOOL RUNS`, so the models see what really happened.

## Subagents

`"subagents": { "explore": 0..2, "test": true|false }` replaces the old fixed deployment of one of each. If the Executor leaves it out, the lab deploys one explorer and the test subagent, as before. With two explorers, each takes an angle (the implementation, and what can go wrong) and they run side by side. Explorers use web search; their task, the searches they report and their findings go into **the pull request description** of the contribution they informed, under "Explorer subagents", with `@` mentions defused so nobody is pinged. The test subagent's commit carries `Model-Role: subagent`. Each deployment is a `tool_runs` row (`subagent_explore`, `subagent_test`); their model cost is already in the ledger.

## Sprite sessions

`"sprite_session": { "purpose": "...", "commands": [ { "run": "...", "timeout_s": 5..120 } ] }`, up to 4 commands, 240 s in all. They run one after another in the model's own Sprite (one per lab, `observable-<lab>`), in `~/lab-session`, through the same `execInSprite` as the contribution check (`api/_lib/sprite-session.ts`):

- the sprite gets the Sprites `defaults` egress policy (GitHub, npm and the usual registries) before anything runs;
- nothing secret goes in: any command or environment value carrying one of this server's credentials is refused before a request is made;
- each command runs under coreutils `timeout`, and its exit status comes from a marker the wrapper prints;
- the commands take the same lock as the contribution check, so they never run while the sprite is testing a branch;
- output is cleaned of ANSI codes and anything that looks like a credential, and the last 1.5 KB per command is stored.

The room shows the stored transcript on the screen above the model's desk. **Cost** is estimated from measured command time at `LAB_SPRITE_USD_PER_HOUR` (default 1.30). That default is a placeholder chosen to be on the high side, not a published Sprites price; set it from the current price list.

## The lab model endpoint

This is not a tool on the menu. It is something a Sprite session comes with when `LAB_ENABLE_LIVE_MODEL=true` (default off), so there is nothing for the Executor to ask for. I added it because the models were building a client for a hosted model and had no model to call. I did not want to hand them my OpenRouter key, so the lab is the host: it serves the endpoint and keeps the key.

While a Sprite session runs, its commands have four more variables: `LAB_MODEL_BASE_URL` and `LAB_MODEL_API_KEY`, and the same two values as `OPENAI_BASE_URL` and `OPENAI_API_KEY`. The base URL is `<origin>/api/live-model/v1`, and it answers two requests in the OpenAI shape:

- `POST <base>/chat/completions` returns one chat completion: `choices[0].message` with `content` and native `tool_calls` (`id`, `type: "function"`, `function.name`, and `function.arguments` always as a string), `finish_reason` and `usage`.
- `GET <base>/models` lists the models it answers for.

**What a request may contain.** The lab builds the request it sends on, field by field, from a short list: `model`, `messages`, `tools`, `tool_choice`, `max_tokens` or `max_completion_tokens` (never more than 4096), and `temperature` and `response_format` when the model's entry in the OpenRouter catalog lists them. Everything else is dropped before the request leaves the server. That is what keeps provider routing, plugins, transforms, fallback model lists and other people's keys out of a call I pay for. The names of dropped fields come back in the `X-Lab-Dropped-Fields` header. Messages are text only, at most 200 of them, and the whole request may be 256 KB. `"stream": true` is refused with a 400, because the endpoint is non-streaming only. The model must be one of `LAB_LIVE_MODEL_IDS` (default `google/gemini-3.8-flash`), spelled exactly. Any other model gets a 400 that names the ones allowed. Two kinds of id can never be on the list, even if I put them there, because they let OpenRouter change what is called: an id with a `:` suffix such as `:online`, and anything under `openrouter/` such as `openrouter/auto`, which picks a model by itself at a price I did not choose.

The body has to be sent with `Content-Type: application/json`. Vercel only reads a body as JSON when the header says so: with no header it reads nothing, and with the form type that Python's `urllib` adds by itself it turns the JSON into something else. Either way the request used to be refused with a message about the wrong thing. Now it gets a 415 that says to send the header, and no call is counted.

One thing travels inside a message besides its text and tool calls: `reasoning_details`. This is the list OpenRouter returns next to an assistant message, and for some models it is not optional. Gemini puts its thought signatures there, and as far as I know it refuses the next request of a tool loop if the assistant turn comes back without them. So the answer carries `reasoning_details` when the model returns them, and an assistant message may bring them back. Both ways the entries are rebuilt from the documented fields (`type`, `id`, `format`, `index`, `text`, `summary`, `data`, `signature`), at most 64 per message, and never cut, because a cut signature no longer verifies. Coming back from the model, the list stops at 128 KB. I have not run a two round tool loop against the real Gemini through this endpoint yet, so that it now passes is my reading of the documentation, not something I watched.

**The key.** A key is 256 random bits with `labk_` in front. The database holds only its SHA-256 hash, with the experiment, epoch, model and Sprite it was issued to. It ends when the session ends, and after 15 minutes at the latest. It allows 20 calls, one at a time, and $0.25. An expired, revoked or unknown key gets a 401 with a short reason. A key that has used its calls or its money, or that already has a call running, gets a 429.

The limits are held by the database. A call is let through by one conditional `UPDATE` that counts it, checks expiry, revocation and both limits, and takes the key's single in-flight slot, all in one statement. Two calls that arrive together cannot both get past a limit. Because only one call per key runs at a time, and what a call costs is only known once it is billed, the dollar limit can be passed by one call at most.

**Getting the key into the Sprite.** This is the one place where something shaped like a credential goes into a Sprite, so the exception is narrow and written down in `api/_lib/sprites.ts`. `execInSprite` has a separate option for it. That option only accepts a value in the scoped key format and an `https` base URL, and the ordinary environment option still refuses any name that looks like a key, these four included. The check that stops this server's own credentials from being sent still runs on every value. Output from the session has the key removed before it is stored.

Every other command the lab runs in a Sprite gets `CI=true`. A command that holds the key does not. The models are told the key is never present in CI, and code that keeps to its fixture whenever `CI` is set would otherwise never call the endpoint. A session that did not get a key runs with `CI=true` as before.

**Egress.** Sprites normally get the Sprites `defaults` policy and nothing else. For the length of a session with the endpoint on, the lab adds one rule that allows its own host, `{ "domain": "<host>", "action": "allow" }`, which is the format in the [Sprites networking documentation](https://docs.fly.io/sprites/concepts/networking). The order matters: the rule is applied first, the lab reads back that the Sprite has it, and only then is a key made. If the Sprite does not confirm the rule, no key is made and the session runs as it does with the endpoint off. When the session ends, the key is revoked and the policy goes back to `defaults`. The [API reference](https://docs.fly.io/sprites/api/network-policy/set-network-policy) documents that both setting and reading the policy answer with the same `{ "rules": [...] }` shape the code reads back. I have not watched this happen on a real Sprite yet.

Two limits of this. The policy works through DNS: a host that is not allowed does not resolve, and an address can be reached only if an allowed host resolved to it. The lab is on Vercel, and Vercel serves many sites from the same addresses, so while the rule is in place a Sprite may be able to reach another Vercel site through those addresses by asking for a different host name. I have not tested whether that works. A custom domain would not change it, because it resolves to the same addresses. The Sprite holds nothing of mine except the scoped key, and the rule is gone when the session ends. The other limit: anything that sets up a Sprite again puts the policy back to `defaults`, so if I run `create`, `create_all` or `setup` on `/api/sprites` while a session is running, the rest of that session cannot reach the endpoint and its record still says a key was offered.

**Spend.** Before a call the lab checks `LAB_DAILY_BUDGET_USD`, then the endpoint's own cap, `LAB_LIVE_MODEL_DAILY_USD` (default 1, UTC day). After it, what OpenRouter reports as `usage.cost` is written to `model_calls` with purpose `live_model`, under the experiment and epoch the key was issued to, and added to the key. No price table is involved. If a response comes back without `usage.cost`, it is recorded as costing nothing with `cost_source` `none`, and the 20 call limit is what bounds it. A call I gave up waiting for (90 s) is recorded as costing nothing too, although OpenRouter may still bill it. A Sprite session's worst case for the budget check includes the key's $0.25.

**The record.** Every call is a row in `live_model_calls`: the key, experiment, epoch, the model and Sprite it was issued to, the model asked for and the one that served, status, token counts, cost and duration, with a 200 character excerpt of the last user message and of the answer and the names of any tools called. Whole conversations are not kept. The session's `tool_runs` row gets `detail.live_model` with whether a key was offered, how many calls it made and what they cost. A call that failed upstream still counts against the key's 20.

The session's stored output ends with one line about the endpoint, for example `lab model endpoint: 2 calls, $0.0200`, or `lab model endpoint: not available in this session, no key was made: ...` with the reason. The models read the end of that output in later rounds, and the Commentator is told the same in the round itself. This matters because the prompt can only say the endpoint is switched on. Whether a session really got a key is decided by the Sprite when it confirms the egress rule.

Revoking a key stops new calls. It does not stop a call that is already with the model: that one finishes and is settled on the revoked key. So when a call is still running as the session ends, the lab waits up to 10 seconds for it before it writes the session's totals. If the call takes longer, `detail.live_model` has `call_in_flight: true`, the output line says the figure is short by one call, and the spend ledger and `live_model_calls` are where the real cost is.

**What the models are told.** One paragraph, and only while the endpoint is switched on for Sprite sessions: the variable names, that a session has them when the lab could open the endpoint for it and that the session's output says so when it could not, the models, the limits, that it is non-streaming and wants a JSON content type, that `reasoning_details` go back with a tool call turn, that CI and the contribution check get no key and keep their localhost fixture, that a session with the key is not given `CI`, and that what a model answers through it is untrusted data. It says nothing about what to do with it.

## GPU jobs

`"gpu_job": { "purpose": "...", "script": "..." }`, one Python script of at most 20,000 characters, run by `modal/gpu_jobs.py` under the research runner's sandbox rules:

- the script must compile under the runner's Python first; a syntax error comes back at stage `syntax` and no GPU is started;
- it runs in a fresh Modal Sandbox on an A10G with the network blocked, no secrets, no volumes (unless it names [public weights](#public-weights) or a [public dataset](#public-datasets), see below), CPU and memory limits, and a hard limit of 120 s; the sandbox is always terminated;
- its output goes to a size-limited file and only the last 64 KiB is read back, from one verified regular file;
- whatever it prints is self-reported and stored as output, nothing more.

Deploy it with `modal deploy modal/gpu_jobs.py`, create the Modal secret `oblab-gpu-jobs-auth` with `JOBS_TOKEN` (at least 32 characters), and put the same value in the server's `GPU_JOBS_TOKEN`. Set `GPU_JOBS_START_URL` and `GPU_JOBS_STATUS_URL` to the `https://` endpoints Modal prints. The token travels in the Authorization header only. The server spawns the job and polls for up to `LAB_GPU_JOB_POLL_MAX_MS` (default 300000).

**Cost** is the job's measured wall time at `LAB_MODAL_GPU_USD_PER_SECOND`, default **0.000306** (Modal's published A10G rate when this was written; check modal.com/pricing and set it if it has changed). The whole job time is billed at the GPU rate, which slightly overestimates. A job that never started costs nothing; one whose result was lost is charged 210 s.

## Public weights

A GPU job's script has no network, and it must stay that way. With a connection it could download a trained model and print a great score as if it had trained one, and the experiment would mean nothing. So a model cannot download anything. What it can do, while `LAB_ENABLE_WEIGHTS=true`, is ask: `"weights": { "repo": "org/name", "revision": "..." }` names one public Hugging Face model repository (the revision is optional and defaults to `main`). My own code fetches it, checks it, and puts it on a shelf. A GPU job that names it, `"gpu_job": { ..., "weights": "org/name" }`, then reads it. Weights asked for in the same answer are fetched before the job that names them starts.

**Who does what.** The request is read strictly by the server (`api/_lib/weights.ts`): the id must be `org/name` in Hugging Face's own spelling, with no slashes, dots or anything else that could be a path. The server sends it to `fetch_weights` in `modal/gpu_jobs.py`, through the same endpoint and token as GPU jobs, with the token in the Authorization header only. `fetch_weights` is lab code. It is the only code in that app that downloads anything, it holds no credentials of any kind, and it never runs, imports or unpickles what it downloads. The model's script still runs in the sandbox with the network blocked.

**What the fetcher checks, in this order, before it downloads any weights.** It asks the public Hugging Face API for that revision, without a token, and gets back a commit sha and the file list. Then:

1. The repository must be public and not gated. No Hugging Face token is used anywhere, so a gated or private repository could not be read anyway; it looks the same as one that does not exist.
2. Every license the model card states must be on my list: `LAB_WEIGHTS_LICENSES`, default apache-2.0, mit, bsd-3-clause, bsd-2-clause, cc-by-4.0. No license stated is a refusal. The defaults apply only when the variable is not set: entries that are not license ids are left out, and a list with no usable entry turns the tool off rather than meaning the defaults.
3. No custom code. A `.py` file anywhere in the repository, or an `auto_map` entry in its config, is a refusal. I never use `trust_remote_code`.
4. It must have safetensors weights. Only safetensors, JSON, `.txt` and the tokenizer model files (`tokenizer.model`, `spiece.model`, `sentencepiece.bpe.model`) are downloaded. `.bin`, `.pt`, `.pkl` and every other kind of file stay on the hub. A repository with only pickle weights is refused.
5. The files to download must total at most `LAB_WEIGHTS_MAX_GB` (default 3, where 1 GB is 10^9 bytes), in at most 64 files with plain paths.

Then it downloads that exact commit, small files first. Every file must be the size the hub said and hash to what the hub published for it (the sha256 for a large file, the git blob id for a small one). Each downloaded config is read again for `auto_map` before the weights are fetched. Anything that does not match removes the whole download.

**The shelf.** The files go to the Modal Volume `oblab-weights` at `<org>/<name>/<commit sha>/`, with a manifest, `_lab_manifest.json`: the repository, the commit, the license, the total size, each file with its size and sha256, when it was fetched, and that no token was used. Weights already on the shelf are not downloaded again, but the rules are checked again each time they are asked for. The shelf holds `LAB_WEIGHTS_SHELF_GB` (default 30). When a new download needs room, the least recently used entries are removed, where use means being asked for or being named by a job. An entry used in the last 300 s is never removed, since a job may be about to mount it; a download that could only fit by removing one is refused (`shelf`).

**What a job sees.** A job that names weights gets that one shelf entry, and nothing else from the shelf, mounted read-only at `/weights` (the same path is in `LAB_WEIGHTS_DIR`). The network stays blocked, there are still no secrets, and the 120 s limit still applies. If the weights are not on the shelf, or their license has since been taken off my list, the job is not started and no GPU time is spent. Before the script is put in the sandbox, the controller reads the manifest at `/weights` from inside it; if that is not the commit it found on the shelf (the entry was removed in between, and Modal mounts an empty directory for a path that is gone), the script is not run and the result is stage `mount`. A job that names no weights has no volume at all, exactly as before.

**The label.** While this is on, every GPU job result is stored with a label: `fine-tuned from <repo>@<commit>` or `from scratch`. It is at the front of the job's `request_summary`, so it shows on the ticket by the gauge and in the activity record, and in full in `detail.label`. The label is built from what the Modal controller reports it mounted, never from what the model asked for or printed, and the controller reports weights only after the sandbox itself has read their manifest. A job whose script never ran has no label. A sandbox with nothing mounted has no network and no files from outside, so `from scratch` holds. What the job prints is still self-reported and unverified, as before.

**Limits to keep in mind.** `fine-tuned from` says which weights the job could read. It does not show that the job used them, or how. The license check reads what the model card says; it does not judge whether the card is right. A refusal comes back with its rule (`gated`, `license`, `custom_code`, `format`, `size`, `not_public`, `repo`, `revision`, `paths`, `files`, `shelf`) and is stored as a `failed` tool run with the reason. The reason never repeats a name that failed its check (a file path I do not accept, a license that does not have the shape of a license id, a `.py` file with such a path), and the server keeps only letters, digits, spaces and plain punctuation of what the fetcher says: the next epoch's models read that record, and a repository is written by a stranger.

**Waiting.** The server polls a fetch for `LAB_WEIGHTS_POLL_MAX_MS` (default 180000, at most 300000). If it is still running then, it carries on at Modal for up to 900 s, the run is stored as `timeout`, and the job that named those weights is skipped for this epoch. Asking again in a later epoch finds them on the shelf. Only a job that names the repository being fetched waits for it; any other job starts at once. The fetch and the job that waits share the job's own wait (`LAB_GPU_JOB_POLL_MAX_MS`, default 300 s), so if the fetch leaves less than 150 s of it the job is skipped for this epoch too, with the weights already on the shelf.

**Cost.** The fetcher runs on CPU. I charge its measured time at `LAB_MODAL_GPU_USD_PER_SECOND`, the same rate as a GPU job, which is about ten times Modal's listed CPU price, so the estimate errs high. A fetch whose time never came back is charged 960 s. It is written to `model_calls` as `tool/weights`. Storage is separate and not in the ledger: Modal's pricing page listed Volumes at $0.09 per GiB per month with 1 TiB per month free when I read it on 18 November 2026, so a 30 GB shelf costs nothing inside that allowance and about $2.50 a month outside it. Check modal.com/pricing before relying on that.

**What the models are told.** One line in the shared context and a few in the Executor's instructions, only while it is on: what can be asked for, the rules above with my current numbers, that a job reads the weights read-only at `/weights` with the network still off and the 120 s limit, the shelf size, that a fetch and the job that waits for it share one wait, and how results are labelled. It says nothing about which weights to ask for or what to do with them.

The research loop (`modal/research_runner.py`) does not get the shelf. Its kept scores compare runs that all start from nothing, and I did not want to change what those numbers mean.

## Public datasets

A model's code has no network anywhere in this lab: not in a GPU job, not in the research loop, and a Tinker training request holds data and no code at all. So until now a model could only train on data it wrote into its own answer. While `LAB_ENABLE_DATASETS=true` it can also ask for a public dataset: `"datasets": { "repo": "org/name", "revision": "..." }` names one public Hugging Face **dataset** repository (the revision is optional and defaults to `main`). My own code fetches it, checks it, and puts it on a shelf, the same way as [public weights](#public-weights). Nothing a model wrote does the downloading, and nothing downloaded is ever run.

**Who does what.** The request is read strictly by the server (`api/_lib/datasets.ts`): the id must be `org/name` in Hugging Face's own spelling. The server sends it to `fetch_dataset` in `modal/datasets.py`, a Modal app of its own with its own two endpoints and token (`DATASETS_START_URL`, `DATASETS_STATUS_URL`, `DATASETS_TOKEN`; the token travels in the Authorization header only). That app has three functions of mine and nothing else:

- `fetch_dataset` is the only one with the network. It holds no credentials of any kind, there is no Hugging Face token anywhere, and it does not open what it downloads: it only writes the bytes and checks their hashes.
- `describe_files` counts rows and reads column names for the manifest, and `read_rows` reads rows for a training run. Both parse files a stranger wrote, so both run with the network blocked, no secrets, no access to my other Modal resources, the shelf mounted read-only, and a fresh container for every call. They open files as data: there is no `datasets` library, no loading script, no pickle and no `eval` in that app.

**What the fetcher checks, in this order, before it downloads anything.** It asks the public Hugging Face API for that revision of the dataset, without a token, and gets back a commit sha and the file list. Then:

1. The dataset must be public and not gated. A gated or private one cannot be read without a token, and looks the same as one that does not exist.
2. Every license its card states must be on my list: `LAB_DATASETS_LICENSES`, default apache-2.0, mit, cc-by-4.0, cc-by-sa-4.0, cc0-1.0, odc-by, bsd-3-clause. No license stated is a refusal. The defaults apply only when the variable is not set: entries that are not license ids are left out, and a list with no usable entry turns the tool off rather than meaning the defaults.
3. Only data files are downloaded, chosen by the end of the file name: `.parquet`, `.jsonl`, `.json`, `.csv`, `.tsv`, `.txt` and `.arrow`. Everything else stays on the hub: loading scripts, any `.py`, notebooks, archives, compressed files, pickles, images, audio, the card. A dataset that has none of the seven kinds (one that exists only as a loading script, say, or as a zip) is refused, because I never run a loading script. A dataset that has a script next to its data files is fetched without the script.
4. The data files must total at most `LAB_DATASETS_MAX_GB` (default 1, where 1 GB is 10^9 bytes), in at most 200 files with plain paths.

Then it downloads that exact commit. Every file must be the size the hub said and hash to what the hub published for it (the sha256 for a large file, the git blob id for a small one). Anything that does not match removes the whole download.

**The shelf.** The files go to the Modal Volume `oblab-datasets` at `<org>/<name>/<commit sha>/`, laid out as in the repository, with a manifest, `_lab_manifest.json`: the repository, the commit, the license, the total size, each file with its kind, size and sha256, how many of the repository's files were left on the hub, when it was fetched, and that no token was used. The manifest also has each file's rows and column names, and the rows in all, where my reader could count them inside two minutes; where it could not, the value is null. A dataset already on the shelf is not downloaded again, but the rules are checked again each time it is asked for. The shelf holds `LAB_DATASETS_SHELF_GB` (default 20). When a new download needs room, the least recently used entries are removed, where use means being asked for, being named by a GPU job, or being read for a training run. An entry used in the last 300 s is never removed; a download that could only fit by removing one is refused (`shelf`).

**Use 1: a GPU job reads it.** `"gpu_job": { ..., "dataset": "org/name" }` (or `"org/name@<commit>"`) gives the job that one shelf entry, and nothing else from the shelf, mounted read-only at `/datasets` (the same path is in `LAB_DATASETS_DIR`). The network stays blocked, there are still no secrets, and the 120 s limit still applies. The sandbox of such a job also has pyarrow installed so the script can read parquet and arrow files; a job that names no dataset runs in the image it always had and has no `/datasets`. If the dataset is not on the shelf, or its license has since been taken off my list, the job is not started and no GPU time is spent (stage `dataset`). As with weights, the controller reads the manifest at `/datasets` from inside the sandbox before the script is put there, and does not run the script if it is not the commit it found (stage `mount`). A dataset asked for in the same answer is fetched before the job that names it starts, and the two share the job's one wait. A job may name weights and a dataset together.

The job's stored result is labelled `data from <repo>@<commit>`: at the front of its `request_summary` and in `detail.dataset_label`, with the mounted entry in `detail.dataset`. The label is built from what the controller mounted, never from what the model asked for or printed. It says which data the job could read. It does not show that the job read it, or what it did with it, and what the job prints is still self-reported.

**Use 2: a Tinker training run takes its examples from it.** In place of `"examples"`, a [Tinker training](#tinker-training) request may hold:

```
"dataset": {
  "repo": "org/name",                 or "org/name@<commit>"; it must already be on the shelf
  "file": "data/train.jsonl",         needed when the dataset holds more than one file with rows
  "user_column": "question",          the column that becomes the user turn
  "assistant_column": "answer",       the column that becomes the assistant turn
  "system": "text of the model's own, put before every row as a system message (optional, at most 2000 bytes)",
  "limit": 500                        rows to use, 10 to 2000 (optional, 500 when left out)
}
```

The request is read as strictly as the inline form, with the same base model and settings rules; giving both `examples` and `dataset` is a refusal. The Reviewer rules on it like any training run, and is told plainly that neither it nor the lab has seen the rows yet. After approval, in this order:

1. My reader on Modal (`read_rows`) reads the file. It takes the first rows that fit, in file order: each row becomes one user turn and one assistant turn, with the cell text exactly as it is in the file. A row is left out, and counted by reason, when a column is missing, a cell is not text, a cell is empty, the text holds a control character or broken bytes, the row would pass 6,000 bytes, or it repeats an earlier row. Reading stops at the row limit, at 120,000 bytes of text in all, at the end of the file, or after 50,000 rows looked at. Nothing is cut to fit. Only top-level columns that hold text can be mapped, and only ones with plain names (letters, digits, underscore, dot, hyphen and space, at most 64 characters); a `.txt` file has no columns, and a `.json` file must be a list of rows and at most 64 MB.
2. The server puts those rows through the same code that reads inline examples (`normalizeTinkerRequest`), so every check a model's own data gets is made on these too: the format, the per-example and total size, 10 to 2,000 examples, no two alike, the step limit. It does not trust the rows because my reader sent them.
3. The cost estimate is made from the rows that were really read, with the same formula, and the run is refused above `LAB_TINKER_RUN_USD`. Only then is the estimate set aside under `LAB_TINKER_DAILY_USD`, and the run starts. From here it is the same run as any other: the runner holds out about a tenth of the rows with a salt the model never sees, and measures the loss before and after.

A read costs Modal time whether or not a run comes of it, and a read that is refused (a column that is not there, a file that needs naming, too few rows that fit) opens no run, so `LAB_TINKER_PER_DAY` alone would never count it. Reads therefore have a daily limit of their own, set to the same number: a UTC day holds as many reads as it may hold training runs (default 2), counted from the stored `dataset_rows` rows, whatever came of each. Past it the request is refused before anything is asked of Modal, with the reason stored. A request the Reviewer did not approve reads nothing and uses none of them.

The Tinker key is never near the files. The reader has no key and no network, and it hands the examples back to the server; the runner that holds the key gets examples, exactly as it does for an inline request, and reads no file.

The run's record names where its examples came from: `detail.dataset.source` on the `tinker_train` row holds the repository, the commit, the license, the file, the two columns, whether a system message was added, the limit, the rows looked at, used and left out by reason, why reading stopped, and that the order was the first rows that fit. The rows themselves are not stored; the hash of the examples as read is, as for inline data. The read is also its own row, `dataset_rows`, with what it cost. The public list of adapters shows `data_from: "<repo>@<commit>"` for such an adapter, and a kept adapter's manifest carries the same source.

**Such an adapter is not offered to visitors.** For inline data the Reviewer sees every example before it approves. For a dataset run nobody has read the rows: not a model, not the Reviewer and not me. So the [visitor chat](#talking-to-a-trained-adapter) leaves an adapter trained on dataset rows off its list, and a message that names one is answered 404 `not_offered` before anything is set aside or sent. `LAB_TRAINED_CHAT_DATASET_ADAPTERS=true` (default false) is my separate switch to offer them. With it on, the panel says for each such adapter which dataset it was trained on and that nobody at the lab has read those rows, and the notice beside the chat changes to say that some of the models were trained on rows of a public dataset nobody at the lab has read. The lab model endpoint is not changed by this: the models can still call such an adapter there while `LAB_ENABLE_LIVE_TRAINED` is on.

**Limits to keep in mind.** The license check reads what the dataset card says; it does not judge whether the card is right, or whether every row in the dataset is the uploader's to license. Hugging Face's own converted copies live on a revision with a slash in its name (`refs/convert/parquet`), which my revision rule does not accept, so a dataset is fetched in the form its author uploaded. Old datasets with no organisation in their id (like `squad`) must be asked for by their full `org/name`. A dataset is fetched whole or not at all: there is no way to ask for one folder of a large one. Rows are taken from the start of a file, which is not a random sample. File names and column names come from the dataset's author and are shown to the models in the fetch's record; they are held to plain characters (column names to 64), and they are shown as data, but they are still words a stranger chose. A name that failed its check is never repeated: a refusal for a file path I do not accept says so without the path, a license that does not have the shape of a license id is called "a license id the lab cannot read", and when a parser fails on a file only the kind of error is passed on, not its message, which could quote the file. On top of that the server keeps only letters, digits, spaces and plain punctuation of anything the fetcher or the reader says before it stores it, and names as removed from the shelf only entries of the form `org/name@<commit>`. The stored record of a refusal is read by all five models in the next epoch, so it must not be a place where a dataset's author can write to them. What a GPU job prints from a dataset, and the few samples a training run stores, are shown to visitors like any other output. A refusal comes back with its rule (`gated`, `not_public`, `license`, `format`, `size`, `files`, `paths`, `repo`, `revision`, `shelf`) and is stored as a `failed` tool run with the reason.

**Waiting.** The server polls a fetch for `LAB_DATASETS_POLL_MAX_MS` (default 180000, at most 300000). If it is still running then, it carries on at Modal for up to 900 s and the run is stored as `timeout`; asking again later finds it on the shelf. A read for a training run is given `LAB_DATASETS_READ_POLL_MAX_MS` (default 150000, at most 240000); if the reader has not answered by then the run is not started, and the reason is stored. The read and the run share the run's own wait (`LAB_TINKER_POLL_MAX_MS`), so the pair holds the follow-up no longer than a training run alone did; a run still training when it ends is collected by a later tick, as always.

**Cost.** The fetcher and the reader run on CPU. I charge their measured time at `LAB_MODAL_GPU_USD_PER_SECOND`, the same rate as a GPU job, which is about ten times Modal's listed CPU price, so the estimate errs high. A fetch whose time never came back is charged 960 s and a read 360 s. They are written to `model_calls` as `tool/datasets` and `tool/dataset_rows`. Storage is separate and not in the ledger: Modal's pricing page listed Volumes at $0.09 per GiB per month with 1 TiB per month free when I read it on 18 November 2026, so a 20 GB shelf costs nothing inside that allowance and under $2 a month outside it.

**What the models are told.** One line in the shared context and a few in the Executor's instructions, only while it is on: what can be asked for, the rules above with my current numbers, and, only for the readers that are switched on, how a GPU job reads a dataset and how a training request names one, with the daily limit on reads. It says nothing about which dataset to ask for or what to do with one.

The research loop (`modal/research_runner.py`) does not get the shelf. It keeps its one fixed dataset, so its kept scores go on meaning the same thing.

## Tinker training

While `LAB_ENABLE_TINKER=true`, the Executor may ask for one fine-tuning run on [Tinker](https://tinker-docs.thinkingmachines.ai/), the training service from Thinking Machines. It is LoRA only: a small adapter is trained on top of an open-weight base model, and the base model's own weights are not changed. The model does not write a training script. It writes the data and a few bounded settings, and my own code does the rest.

```
"tinker_train": {
  "purpose": "one line",
  "base_model": "Qwen/Qwen3.5-4B",
  "examples": [ { "messages": [ { "role": "user", "content": "..." }, { "role": "assistant", "content": "..." } ] }, ... ],
  "settings": { "rank": 16, "learning_rate": 0.0002, "epochs": 2, "batch_size": 8 }
}
```

**What a request may hold.** It is read strictly (`api/_lib/tinker.ts`), and anything that is not exactly this refuses the whole request with a reason. Nothing is cut to fit.

- `base_model` is optional and must be on my allowlist, `LAB_TINKER_BASE_MODELS`. The default list is `Qwen/Qwen3.5-4B`, the cheapest current chat model to train on Tinker's price table and the one Tinker's own first tutorial uses. I can also allow `Qwen/Qwen3.5-9B` and `Qwen/Qwen3.6-35B-A3B`. Those three are the models I have a published price and a chat format for; an id that is not one of them is left out of the list, and a list with nothing usable turns the tool off. None of the three was marked as retiring when I read the table on 18 November 2026.
- `examples`: 10 to 2000 different conversations. Each is 2 to 12 messages: an optional system message, then user and assistant in turn, ending with the assistant. Text only. At most 6000 bytes of text in one example and 120000 in all. The dataset is part of the Executor's answer, which the Challenger and the Reviewer read whole, so in practice it is as large as an answer can be, a few hundred short examples at most. Two identical examples are refused, because a copy could land on both sides of the held-out split.
- `settings` are optional and bounded: `rank` 8, 16 or 32 (default 16), `learning_rate` 0.00001 to 0.0005 (default 0.0002), `epochs` 1 to 3 (default 2), `batch_size` 1 to 16 (default 8), and at most 600 optimizer steps in all.
- Only the last assistant message of each example is trained on. That is how Tinker's cookbook says to train a chat model whose format puts a thinking block before each answer; earlier assistant turns are context.
- While [public datasets](#public-datasets) are on, a request may hold `"dataset"` in place of `"examples"`: a dataset on my shelf, the two columns that become the user and assistant turns, and a row limit. My own reader turns the rows into examples, and from there the request is read, estimated, capped and run exactly as above. While they are off, `"dataset"` is an unknown field and refuses the request, as it always did.

**Who approves it.** The Reviewer, the same way it rules on an exhibit: it is told the base model, the number of examples and bytes, the settings, the number of steps and my estimate of the most the run could cost, and nothing starts unless it answers `"tool_verdicts": { "tinker_train": "approve" }`. Like the other deliverables, the run happens after the epoch, in the follow-up.

**The cost, before.** Tinker returns no cost with a call, its billing page lags by hours, and its keys cannot carry a spending limit. So every dollar figure for Tinker in this lab is an **estimate**: token counts times the price Tinker published, per million tokens, copied into `api/_lib/tinker.ts` on 18 November 2026 (for `Qwen/Qwen3.5-4B`: train $0.737, sample $1.005, prefill $0.33). It is never a billed amount, and the records say so.

Before a run starts, the server works out the most it could cost from the text alone: one token for every byte of text plus some for the chat format, every epoch over the whole dataset, two passes over the largest examples the held-out slice could hold (a forward pass by a training client is billed at the train price), the samples at their longest, and a quarter on top. A token for every byte is a ceiling: the tokenizer never makes more tokens than there are bytes. Measured with the real tokenizer, ordinary prose takes a fifth to a third of that, and text that is mostly digits takes nearly all of it (0.95). So the amount set aside is usually several times what the run then costs, and the difference is given back when the run is settled. Some sizes, for scale: 200 two-line examples of prose for 2 epochs set aside about 6 cents on `Qwen/Qwen3.5-4B`. A full 120000 bytes in a few hundred examples for 3 epochs sets aside about $0.38 on `Qwen/Qwen3.5-4B` and about $0.75 on `Qwen/Qwen3.5-9B`. The most the limits allow at all, 2000 examples of 12 very short messages for 3 epochs on `Qwen/Qwen3.5-9B`, comes to about $1.97, still under the $2 a run may cost. Then, in this order:

1. If that is over `LAB_TINKER_RUN_USD` (default $2), the run is refused.
2. The runs-per-day limit (`LAB_TINKER_PER_DAY`, default 2) and the lab's own daily budget are checked, against that same worst case. The limit counts the runs opened that UTC day in `tinker_runs`, so a run that is still training counts from the moment it is opened. A run that was closed at no cost, because it never started or the runner refused it before training, does not count.
3. The estimate is set aside under `LAB_TINKER_DAILY_USD` (default $10 per UTC day) in the database, by one conditional UPDATE that only succeeds while spent plus set aside plus this amount stays within the cap. Two requests arriving together cannot both pass it. This is the same idea as the lab model endpoint's keys.
4. One row is written to `tinker_runs` for the epoch. The table allows one per epoch, so a follow-up that is run twice cannot start two.

**The run, by lab code.** The server sends the examples, the settings, the amount set aside, the prices, the run's own name and a random value it has just made up (`split_salt`) to `modal/tinker_jobs.py`, my own runner on Modal. The Tinker key is a Modal secret there, given to the training function only. The runner:

1. Checks the request again against its own copy of the limits.
2. Splits the dataset by a hash of `split_salt` and each example's position: about a tenth is held out, at least 2 and at most 200 examples. The model wrote its request before that value existed, so it cannot know which examples are held out.
3. Counts real tokens. If the real plan would cost more than the amount set aside, it refuses before anything is trained. Since the amount set aside assumes a token for every byte, this should not happen; it is there so that the amount set aside stays a ceiling whatever the server got wrong.
4. Measures the base model's loss on the held-out examples.
5. Trains, one batch at a time. It stops early at 600 steps, after 30 minutes of training, or when the tokens counted so far, plus what the last measurement and the samples still need, would pass the amount set aside.
6. Measures the trained adapter's loss on the same held-out examples.
7. Saves the adapter for sampling with a time to live (`LAB_TINKER_TTL_DAYS`, default 14), and samples up to three short completions on held-out prompts.

The loss is the mean cross-entropy per trained token, each held-out example counted once. Lower is better. It is **measured by the lab**, on examples the lab chose. That is a different kind of number from the scores in the research loop, which generated code reports about itself and which stay marked unverified.

**The cost, after.** The runner returns the tokens it counted, and the amount set aside is replaced by those tokens times the published prices. A run that failed part way is charged for the tokens it had used. A run whose usage is unknown, because the runner was lost, its answer was unusable or its start was never confirmed, is charged the whole amount set aside, so the record errs high. A run that is known not to have started costs nothing and its money is given back. The estimate is written to `model_calls` as `tool/tinker_train` with `cost_source` `estimate`, so the lab's daily cap counts it, and the epoch's own stored cost is brought up to date from the ledger at the same moment, also when the run is collected long after the epoch was saved.

**Was it started?** Only the runner itself saying no (a 4xx: a wrong token, a job it refuses) counts as a run that did not start. A 5xx or a timeout can come from the gateway in front of the runner after the run was already started, and so can no answer at all, so none of those gives the money back. The runner remembers the call it started under each run's name (a Modal Dict, `oblab-tinker-runs`). When a start is not confirmed, the server asks the runner by that name, straight away and again on later ticks; if the runner knows the run, it carries on as an ordinary run and costs what it measured. If the runner still does not know it after 15 minutes, the run is closed as one whose usage is unknown. A start sent twice for one name starts one run.

**Waiting.** The follow-up polls for `LAB_TINKER_POLL_MAX_MS` (default 300000, at most 480000). A run that is still training then carries on at Modal for up to 45 minutes in all, its money stays set aside, and the next hourly tick collects the result and writes the record. If nothing comes back long after its time limit, the run is closed as lost. The tick collects open runs first, once, before it does anything else, for every experiment and not only the one it is advancing, and it keeps doing so while `LAB_ENABLE_TINKER` is off as long as the runner's address and token are still set. Collecting only asks the runner and closes rows; it starts nothing. That way a run that was training when I switched the tool off, or when its experiment was replaced, still gets its record and its cost on the ledger.

**When an adapter expires.** Tinker counts the time to live from the moment the checkpoint is saved. The server does not know that moment exactly, because a result can be collected hours after it. So it counts from the moment the run was opened, which is always before the save, and takes an hour off. The lab therefore stops offering an adapter a little before Tinker removes it, never after.

**The record.** A `tool_runs` row with tool `tinker_train`, so it is in the public state and the activity panel like a GPU job, and a `tinker_runs` row. Between them: the base model, the dataset's SHA-256, size and number of examples, the settings, the split value, how many examples were trained on and held out, the held-out loss before and after (labelled as measured by the lab), the first and last training loss, steps planned and done and why it stopped early if it did, the tokens counted, the estimated cost and what was set aside, the adapter's name and checkpoint path, when it expires, and the samples. A refusal is stored too, with its reason: by the Reviewer, by a cap, by the strict reading, or by the runner.

**Limits to keep in mind.** The held-out loss says how well the adapter fits data like the data the model wrote. It is not a test of general ability, and near copies in the dataset make it look better than it is; only exact copies are refused. The amount set aside before a run is a ceiling, not a forecast, so the daily Tinker cap fills faster than the money is really spent while a run is open, and loosens again when it is settled. Tinker keeps checkpoints free up to 100 GB or 100 checkpoints per organisation; the time to live is what keeps the lab under that.

**What the models are told.** One line in the shared context and the field in the Executor's instructions, only while the tool is on: what it does, the allowlisted base models, the data and settings limits, the per-run and daily caps, that it is LoRA only, that the scores are measured by the lab on a slice it chooses, that results and adapters are public, and that adapters expire. Nothing about what to train or why.

## Talking to a trained adapter

A kept adapter can be talked to in two places. Both go from this server straight to Tinker's OpenAI-compatible endpoint, with the adapter's checkpoint path as the model (Tinker runs it on the base model it was trained on) and `"reasoning_effort": false`, so the base model answers directly, the way the adapter was trained. One file reads the Tinker key for this, `api/_lib/tinker-chat.ts`, and it goes into one Authorization header.

**On the lab model endpoint** (`LAB_ENABLE_LIVE_TRAINED=true`, with the endpoint itself on). `GET <base>/models` lists each kept adapter as `lab/<name>`, and a call that names one is answered by it. The same scoped key authorises the call and the same limits of that key count it. An adapter takes text messages only (system, user, assistant), at most 1024 tokens of answer, and an optional temperature; tools and every other field are dropped and named in `X-Lab-Dropped-Fields`. The most the call could cost is set aside under `LAB_TINKER_DAILY_USD` first, then replaced by the tokens Tinker reports at the published prices. If the call may have been served without the server learning its token counts (an answer with no usable `usage`, a timeout, a connection that broke part way, a 200 with nothing usable in it), the whole amount set aside is counted instead; only a call that certainly was not served (no connection was made, or Tinker answered with an error) costs nothing. That estimate goes on the ledger as purpose `live_model` with `cost_source` `estimate`, so `LAB_LIVE_MODEL_DAILY_USD` counts it too, and the answer carries `X-Lab-Cost-Basis: estimate`. The models are told this as a fact, in the same line as the tool, only while it is really on.

**In the room** (`LAB_ENABLE_TRAINED_CHAT=true`). A small panel, "Talk to what they trained", lists the kept adapters with their base model, epoch, the model that wrote the data and the held-out loss the lab measured, and has a chat box. Beside it: "A small model fine-tuned by the lab's AI models on data they wrote. Replies are not reviewed." An adapter trained on rows of a [public dataset](#public-datasets) is left off the list and refused by name unless `LAB_TRAINED_CHAT_DATASET_ADAPTERS=true`; when one is listed, the notice says that some were trained on rows of a public dataset nobody at the lab has read. It goes through a public route, `/api/experiment/trained-chat`, and since anyone can call that, everything about a call is bounded (`api/_lib/trained-chat.ts`):

- a message is at most 500 characters, a conversation at most 8 turns, a reply at most 200 tokens;
- one address may send 20 messages in ten minutes and 80 in a UTC day, whatever browser string comes with them. An IPv6 address counts as its /64 network, because a home or a phone is usually given a whole /64 and can pick any address in it;
- within that, one visitor (an address together with a browser string) may send 10 messages in ten minutes and 40 in a UTC day. Both limits must pass. The browser string is whatever the sender says it is, so it only splits the people behind one address from each other; the address limit is the one a script cannot get around by changing it;
- an address and a visitor are remembered only as keyed hashes, new every day. No address is stored or logged;
- all visitor chat together may cost `LAB_TINKER_CHAT_DAILY_USD` a day (default $1), counted inside `LAB_TINKER_DAILY_USD` and the lab's daily budget, set aside before each call in the same way as a run and settled by the same rule as on the lab model endpoint: measured tokens when Tinker reports them, the whole amount set aside when the call may have been served without them. At the cap the chat says so in a plain sentence and opens again at 00:00 UTC. Someone sending from many addresses can still use up that $1 for the day, which closes the chat for everyone until 00:00 UTC; it cannot spend more than that;
- what a visitor writes is sent to Tinker to be answered and is not stored or logged by the lab. A call leaves one row of counts in `trained_chat_calls` (which adapter, how many turns and characters, tokens, the estimated cost) and one line on the spend ledger as purpose `trained_chat`.

The room's own state (`GET /api/experiment`) carries `trained_chat_enabled: true` while the visitor chat is on, and leaves the field out otherwise. The panel calls its route only after it has seen that. With the chat off, which is the default, a visitor's page never calls `/api/experiment/trained-chat` at all.

The models are not told about the visitor chat.

## Naming a trained adapter

While `LAB_ENABLE_TINKER_NAMES=true`, a `tinker_train` request may carry one more optional field, `"name"`: a display name for the adapter that run trains. It is off by default, and while it is off `name` is an unknown field like any other, which refuses the request as it always did, and no name is shown anywhere.

```
"tinker_train": { "purpose": "...", "examples": [ ... ], "name": "Brass Finch" }
```

**The name is a label, not an identity.** The adapter is still `lab/e<epoch>-<8 hex>`. That id is what the model endpoint takes as `model`, what the chat sends a message to, what a keep request names and what every record is stored under. Two adapters can never be confused by their ids, whatever they are called.

**What a name may be** (`api/_lib/tinker-names.ts`). It is read strictly and never changed to fit:

- 2 to 40 characters, only letters (A to Z, a to z), digits, spaces, hyphens, apostrophes and dots. It starts with a letter or digit, has at least two letters, and has no two spaces in a row.
- Nothing that looks like a web address. A dot may be followed by a digit, a space or the end ("v1.5", "Dr. Lin"), not by a letter ("example.com"), and it may not start with www or http.
- Nothing that holds what looks like one of the lab's own ids, anywhere in it: "e41-0a1b2c3d" is refused and so is "e41-0a1b2c3d v2".
- Nothing that reads like a real model or product. Three lists are checked:
  - The models this lab runs (the five of the panel, the fallbacks and the wildcards), by their display names and their ids, as a whole name, with their own version, another one or none: "Grok 4.7", "North", "North 2", "Claude Fable".
  - Family and maker names, anywhere in the name: GPT, ChatGPT, OpenAI, Claude, Anthropic, Gemini, Google, DeepMind, Grok, DeepSeek, Llama, Qwen, Alibaba, Mistral, Mixtral, Nemotron, Nvidia, Microsoft, Copilot, Hugging Face, OpenRouter, Perplexity, Moonshot, Thinking Machines.
  - Names that are also ordinary words or very short, only as a whole word: Sonnet, Opus, Haiku, Fable, Astra, GLM, Kimi, Phi, Ernie, Gemma, Cohere, Codex, Tinker, xAI, o1, o3, o4. "Opus" is refused and "Octopus" is not. A whole word is also the word with a version written straight after it ("Opus4.5", "Fable5.2", "GLM5", "o3mini"), and the word written as two ("x AI").

  Case and separators are ignored, and so are the usual look-alike characters, on both sides of the comparison: i, l and 1 are one letter whatever their case (a capital I and a small l are the same stroke in most typefaces), 0 3 4 5 7 stand for o e a s t, "rn" for m and "vv" for w. So "C1aude", "Ciaude", "GEMlNI", "Gem1ni", "0penAl", "G P T", "gem ini" and "Gr0k" are all refused. This is wide on purpose and it does not keep words apart, so it also refuses a few ordinary names: "Open Aloe" (it begins like "OpenAI" written with a small l) and "William and Mary" ("liam a" is "llama" with an i for an l). The stored reason says which real name it read. Nothing is lost but the label.
- Not the name of another adapter that is still alive, or of a run that is still open. Names are compared the same forgiving way, so "Quiet Lamp" and "quiet-lamp" are one name. The database holds this: there is a unique index on the compared form, so two runs asking for one name at the same moment cannot both get it. A name is free again once its adapter has expired.

**A refused name never refuses the run.** The request stands, the run goes ahead without a name, and the reason is stored in `tool_runs` as a `skipped` row under the tool `tinker_name` (not `tinker_train`, so it never reads as the epoch's run having been dealt with). The list above cannot be complete, so I can also take a name away afterwards: `{"action": "clear_name", "adapter": "lab/..."}` on the operator route below, which is stored too.

**Where a name is shown.** In the visitor chat panel it is the adapter's title, with the lab id under it. In the record of the run (`tool_runs`: the request line, the result line and `detail.name`), which is what the Activity panel and the models' `RECENT TOOL RUNS` are built from. On the lab model endpoint, `GET <base>/models` gives the adapter a `description` with its name; the `id` stays `lab/<id>`. In the manifest of a kept copy. Everywhere it is put on a page as text, never as markup, and it is cleaned like any other stored text on the way out. With the switch turned off again, names already given stay in the database and are shown nowhere.

**What the models are told.** One more sentence in the Tinker line and the `name` field in the Executor's instructions, only while names are on: the alphabet and length, that the name is a label beside the lab id, and that a name that is taken, looks like a web address or reads like a real model or product is refused with the reason stored while the run goes on. Nothing about what to call anything.

## Keeping a trained adapter

An adapter normally expires `LAB_TINKER_TTL_DAYS` (14) after it was trained. While `LAB_ENABLE_TINKER_KEEP=true`, an adapter that is still alive can be marked **kept**. It is off by default; with it off the tool is an unknown tool, nothing about it is in a prompt, the tick makes no query for it and a training run is sent to the runner exactly as before.

**Who can keep.**

- **A model**, as the Executor, with one small request. The Reviewer must approve it, like the other deliverables:

  ```
  "keep_adapter": { "adapter": "lab/e41-0a1b2c3d", "reason": "one line, at most 200 characters" }
  ```

  Exactly those two fields; anything else is refused with the reason stored. The Reviewer is told the lab's own record of that adapter (who trained it, on how many examples, the held-out loss the lab measured, when it expires), how many places are taken, and whether a copy of its weights can be stored. So that a model can name an adapter at all, the shared context lists the adapters that are alive under `TRAINED ADAPTERS`, from the lab's stored runs, only while keeping is on.
- **I can**, through an operator route (`api/experiment/trained-adapters.ts`, `Authorization: Bearer LAB_OPERATOR_SECRET` like the other operator routes): `GET /api/experiment/trained-adapters` shows every adapter that is alive, which are kept, by whom and why; `POST /api/experiment/trained-adapters?confirm=true` with `{"action": "keep", "adapter": "lab/...", "reason": "..."}` keeps one.

**The limits.** They are held by the database, not by arithmetic in the code (`tinker_keeps` in `api/_lib/tinker-store.ts`):

- At most `LAB_TINKER_KEEP_MAX` (default 10, never more than 40) adapters are kept at one time, mine and the models' together. A kept adapter holds a numbered place, the place number is the table's primary key, and a place is taken by one statement that finds the lowest free number only while fewer than the limit exist. Two requests arriving together cannot both take the last place. When every place is taken a request is refused, and only I can make room.
- One epoch may ask for one keep (a unique index on experiment and epoch), and the models together get `LAB_TINKER_KEEPS_PER_DAY` (default 2) a UTC day. My own keeps are not counted against the per-day number, but they do take places.
- An adapter can be kept once. It has to be alive: trained, saved and not expired.

**What keeping does.** Both parts are done by my own runner on Modal (`keeper` in `modal/tinker_jobs.py`), the only place besides the chat file where the Tinker key lives. The request a model writes is two fields of data; no code of a model's runs, and nothing a model wrote goes to Tinker or to the Volume except its one-line reason inside the manifest.

1. **A long life on Tinker.** The runner sets the time to live of the adapter's sampler checkpoint to `LAB_TINKER_KEEP_DAYS` (default 365, 30 to 3650) from that moment, with Tinker's `set_checkpoint_ttl_from_tinker_path`. That is what keeps it answering on the lab model endpoint and in the visitor chat. The lab's own record of when the adapter expires is moved to match. If this step fails the adapter is not kept and its place is given back.
2. **A copy on the lab's own storage.** The runner downloads the adapter's LoRA weights from Tinker and writes them to the Modal Volume `oblab-kept-models`, under `<lab id>/`, as `adapter_config.json` and `adapter_model.safetensors` in PEFT format (the form `peft`, vLLM and SGLang load) with `lab_manifest.json` beside them. A copy may weigh at most `LAB_TINKER_KEEP_MAX_MB` (default 1024; a LoRA of rank 8 to 32 is tens of MB). If the copy fails, the keep still stands and the record says there is no copy and why.

**Why a copy needs the switch to have been on at training time.** Tinker lets a sampler checkpoint be used but not downloaded. Weights can only be downloaded if the training run itself saved them for download (`save_weights_external`) while it was open. So while keeping is on, every training run is asked to save its weights that way too, with the same time to live as the adapter, and the path is stored with the run. An adapter trained while keeping was off has nothing to download: keeping it extends its life and the record says there is no copy. The Reviewer is told which case it is before it rules.

**The conversion to PEFT.** Tinker's export has the two files already, with Tinker's own names for the weights; the cookbook's `build_lora_adapter` renames them to the names of the base model's parameters. For that it needs the base model's `config.json` and the names and shapes of its weights. Given a model's name, the cookbook downloads the whole repository to find them, which is 9 GB for `Qwen/Qwen3.5-4B` and about 70 GB for the largest base model I allow. The runner does not do that: it reads `config.json` and the header of each safetensors file from the public Hugging Face repository (a few hundred KB in all, by byte range, pinned to one revision) and gives the conversion a folder holding just those. No weights of the base model are downloaded and no code from the repository is run. If the conversion fails, the files are stored as Tinker exported them, the manifest says `"format": "tinker"` and why, and I can convert them later with the same cookbook call.

**The manifest** (`lab_manifest.json`) is the lab's own record of the run, written by the lab's code: the lab id and display name, the base model, the Tinker run id and both checkpoint paths, the epoch and the model that wrote the data, its one-line purpose, the dataset's SHA-256, size and number of examples, the settings, the held-out loss before and after as the lab measured it and on how many examples, when it was trained, who kept it, the one-line reason, when, and for the copy its format, files with their sizes and SHA-256, the base model revision the names were converted against, and where on Tinker it came from.

**Tinker's free storage.** Tinker stores 100 checkpoints or 100 GB per organisation for free, and past either a training session is stopped. A kept adapter is one checkpoint for a year instead of two weeks, or two when its copy failed (see below), so `LAB_TINKER_KEEP_MAX` bounds that part at 10, and at 20 if every copy failed. The larger effect is the second checkpoint every run saves while keeping is on: with the defaults (2 runs a day, 14 days) that is up to 56 checkpoints from runs at any time instead of 28, plus the kept ones. After a copy has reached the Volume the downloadable checkpoint is left to expire on its own date; if the copy failed it is given the adapter's long life too, so the copy can still be made, and until then that kept adapter counts as two checkpoints. Unkeeping it and keeping it again once the download works makes the copy and brings it back to one. Every keep stores how many checkpoints the lab's Tinker key holds at that moment, and I check `tinker billing checkpoint-storage` myself. If I raise `LAB_TINKER_PER_DAY` with keeping on, I lower `LAB_TINKER_TTL_DAYS` to stay under 100.

**Cost.** Keeping uses no Tinker tokens: it opens no training session and samples nothing, so nothing is set aside and nothing goes on the spend ledger. A model's request is refused like any tool when the lab's daily budget is already spent. The keeper's own time on Modal is a few seconds of CPU and is not on the ledger. The caps on keeping are counts and sizes: places, requests a day, and MB per copy.

**Waiting.** The request waits 45 seconds for the runner. A keep still going then keeps its place and is collected by a later tick, once, before the tick advances any experiment. If the runner never confirms the start within 90 minutes, or gives no answer within 180, the place is given back and the record says so. Those are long on purpose: the keeper itself is stopped after 15 minutes, but the tick comes once an hour, and one status call that fails must not settle a keep that in fact worked, so the lab asks at two ticks at least before it gives up. A runner that answers that the keep failed is believed at once. A runner that was lost may already have set the long time to live before it stopped; the lab cannot know, so that record says the time to live on Tinker is unknown. Keeping the adapter again settles it.

**How long a keep lasts.** As long as the life it set on Tinker. When that has run out, the adapter is gone like any other: the lab stops offering it, its place is given back by the next tick (or by the next keep request, whichever comes first), and a record is stored under `kept_adapter_expired`. The copy on the Volume stays. To keep one for longer I unkeep it and keep it again before it expires, which sets a fresh time to live and reuses the copy that is already there.

**Unkeeping is mine alone.** `{"action": "unkeep", "adapter": "lab/...", "remove_copy": false}` on the operator route. The runner sets the checkpoint's time to live back to the usual `LAB_TINKER_TTL_DAYS`, counted from now, and the place is free. The copy on the Volume stays unless I pass `"remove_copy": true`. The mark is taken off only after the runner has answered, so a call that times out changes nothing and can be made again. It works with `LAB_ENABLE_TINKER_KEEP` off as well, so a keep can always be undone. No model can unkeep, and nothing a model writes reaches this route.

**Where it shows.** Kept adapters are listed first in the visitor chat panel, the most recently kept at the top, each with a small "kept" mark and a line saying who marked it; the rest follow, newest first. On the lab model endpoint the adapter's `description` says it is kept and by whom. The models see `KEPT by ...` in `TRAINED ADAPTERS`.

**The record.** Every step is a `tool_runs` row, so it is in the public state and the Activity panel: a model's request under `keep_adapter` (kept, refused with the reason, or not kept and why), mine under `owner_keep_adapter`, an unkeep under `owner_unkeep_adapter`, a name I took away under `owner_clear_adapter_name`, and an expiry under `kept_adapter_expired`. A kept row carries who kept it, the reason, the date it is kept until, the time to live that was set, the number of checkpoints the key holds, and for the copy the Volume, folder, format, size and each file's SHA-256. A model's request is stored under the epoch that asked; mine are stored under the adapter's own epoch with the model given as `owner`, which the Activity panel shows as "The owner". The request, the reason and what was done are public.

**Limits to keep in mind.** Keeping says someone wanted this adapter to stay; it says nothing about how good it is beyond the held-out loss already on its record. A copy in PEFT format has been converted by the cookbook's code against the base model's parameter names; I have not loaded one into a serving stack from here, and the first real keep is the first real test of the export, the download and the conversion ([OPERATIONS.md](OPERATIONS.md#naming-and-keeping-trained-adapters) has the check). The copy is the adapter only: using it needs the base model.

**What the models are told.** One line in the shared context and the field in the Executor's instructions, only while keeping is on: that an adapter that is alive can be asked to be kept by its lab id with a one-line reason, that the Reviewer must approve, the per-epoch, per-day and total limits, that only the owner can unkeep, how long a kept adapter stays, that a copy with a manifest is stored and when it cannot be, and that the request and its reason are public. Nothing about which adapter to keep or why. While keeping is on, the training line also stops using the word "kept" for an adapter that has merely not expired yet (it says the adapter stays for 14 days and is alive), so that "kept" means one thing. In the same way, while names are on, the line about the model endpoint says "lab id" where it used to say "name". With both switches off those sentences are word for word what they were.

## The research model talks

This one is not a tool a model asks for. It belongs to the ML research loop (`api/_lib/research-epoch.ts`, `modal/research_runner.py`), and it is off unless `LAB_ENABLE_RESEARCH_TALK=true` and the server knows the runner's models endpoint (`RESEARCH_RUNNER_MODELS_URL`, with the `RESEARCH_RUNNER_TOKEN` it already has). With it off the research loop sends the runner the request it always sent, the runner does what it always did, the prompts are the same, and the route below says it is off without touching the database or the network.

**What it is for.** When the research loop keeps a run as its new best, the lab saves the model that run trained, and a visitor can give it an opening line and read the short piece of story it writes next. It is a tiny model, trained from scratch on children's stories in five minutes, reading and writing one byte at a time. It only writes story-like text.

**How a model gets saved.** The generated `train.py` saves nothing, and in the code the loop has been writing the model is a local variable that is gone when the script ends. The one place my own code sees the model is `prepare.evaluate_bpb`. So for a run that may be kept, the runner appends a fixed block to the sandbox's disposable copy of `prepare.py`. It wraps `evaluate_bpb`, returns what it returned before, and holds on to the last model it scored. When the interpreter exits it writes `torch.save(model)` next to the log in 4 MB parts (the training process may not write a file over 8 MB, and I did not want to change that limit). The controller then copies the parts out through a reader that takes regular files of the stated size only, checks the SHA-256, and writes the model, the `train.py` that made it and a manifest to the Modal Volume `oblab-research-models` as a candidate. The training sandbox never gets that Volume.

What stays the same for such a run: the image, the reviewed harness file and the hash reported for it, the command that starts `train.py`, its 8 MB file limit, its training budget and the hard stop. What is different, so that I do not pretend otherwise: the extra block in the disposable copy, one reference to the last scored model that is held until the process ends, a supervisor that also watches for the moment the save step begins, and a sandbox that may live up to four minutes longer while the parts are copied out. The time the save takes is taken off the measured training wall time, and a save still writing two seconds before the hard stop is cut and the run counts anyway, without a saved model.

**Its limits, which the research models are told as facts while this is on** (and not at all while it is off; nothing in the prompt asks them to do anything about it, and `val_bpb` stays the only thing a run is judged on):

- the lab saves the object last passed to `prepare.evaluate_bpb`, as it is when the process exits. If a run scores one set of weights and ends with another in that object, the second set is saved;
- it is a pickle of the whole module, at most 256 MB, so its classes have to be defined at the top level of `train.py`;
- to load it again the lab runs `train.py`'s definitions without its main part, so a `train.py` with no `if __name__ == "__main__":` guard cannot be loaded;
- it is loaded on a CPU and called as `model(idx)`, with `model(idx, idx)` as a second try, and the scores for the next byte are read from the last position;
- a model that cannot be saved or loaded this way is simply not offered, and the run's score and verdict are the same either way.

**The saved file is self-reported, like the score.** The save runs in the same process as the generated code, which could write anything it liked there. The manifest says so. It carries the epoch, the `val_bpb` the generated code printed (`metrics_source: experiment_stdout_unverified`), the value my `evaluate_bpb` returned for the saved object as seen inside that same process (`eval_bpb_seen_by_harness`, which is not independent either), the parameter count, the context length, the sizes and SHA-256 of the model and of `train.py`, and the harness hash.

**Keeping and the lab's own sample.** After the Reviewer's verdict, and only when the run is kept as the new best and the runner saved its model, the lab asks the runner to promote that candidate. The runner then samples it once by itself (the default opening, 64 bytes) and writes the result beside the model. Only a model whose sample worked is offered to visitors. The Volume holds the newest 3 kept models and at most 3 candidates no older than three days; older ones are removed.

**Where the model runs.** Loading it means running model-written code: `train.py`'s definitions and a pickle. That happens in one place only, a fresh Modal Sandbox per story with the network blocked, no secrets, no GPU, and nothing mounted but that one model's directory, read-only. A fixed script of mine in there loads the model and writes bytes; the controller outside takes only the new bytes, keeps printable ASCII and line breaks, and cuts them to length. Loading and writing together get 60 seconds, the writing itself 40. Nothing model-written is ever loaded on the Vercel server or in a Modal container that holds a credential.

**In the room.** The "Talk to what they trained" panel gets a section headed "The research loop's best story model (epoch N, val_bpb X, self-reported)", with the line "A tiny model trained from scratch on children's stories in five minutes. It only writes story-like text.", the notice "It does not answer questions. It carries on from the line you give it, and nobody reviews what it writes.", a one-line box and the story. If the loop has since kept a better run whose model could not be saved or loaded, the heading drops the word "best" and the section says so, so that an older model is not passed off as the best. A model I trained by hand (see OPERATIONS.md) is labelled as that. The room's state (`GET /api/experiment`) carries `research_talk_enabled: true` while this is on and leaves the field out otherwise; the section calls its route only after it has seen that.

**The visitor route**, `/api/experiment/research-talk`, is public, so everything about a call is bounded (`api/_lib/research-talk.ts`):

- one line of at most 200 characters, made plain ASCII before it is sent (the model was trained on plain English bytes); an empty line means "Once upon a time";
- at most `LAB_RESEARCH_TALK_MAX_NEW` new bytes (default 200, never more than 500). The model's tokens are single bytes, so 200 is about forty words. It stops early at an empty line, which is where a story ends in its training text;
- one visitor (an address together with a browser string) may ask for 3 stories in ten minutes and 10 in a day; one address, whatever browser string comes with it, for 6 and 20. Both must pass, and they are counted by keyed hashes that change every day, as in the trained chat. No address is stored or logged;
- all visitors together may ask for `LAB_RESEARCH_TALK_DAILY` stories a UTC day (default 200, never more than 2000). Someone sending from many addresses can use that up for the day, which closes the box for everyone until 00:00 UTC; it cannot go past it;
- each story is written to the spend ledger as `tool/research_talk` at a flat estimate, `LAB_RESEARCH_TALK_USD_PER_STORY` (default $0.005, which I believe is several times what a one-core sandbox for half a minute costs), purpose `research_talk`, so stories count inside `LAB_DAILY_BUDGET_USD` and stop when that is reached. Modal's bill is not read back;
- what a visitor writes is sent to the runner to be continued and is not stored or logged by the lab. My code on Modal does not print or keep it either: it is written to a file inside the sandbox, which is gone when the sandbox ends. Modal handles it as the argument of a function call, as it does any other. A call leaves one row of counts in `research_talk_calls` (which model, how many characters in and bytes out, how it stopped, the estimate, how long it took). When a story fails, the log line names the stage and nothing else.

**What is recorded.** On the epoch's row, `research_run.keep_key` (the key the run was started with), `research_run.result.checkpoint` (saved or not, why not, size, SHA-256, parameters, the seconds the save and the copy took) and `research_run.promotion` (kept for visitors or not, when, and the runner's reason if not). The epoch's finding page in the research repository gets one line, "Saved model", saying the same. On the Volume, each model's `manifest.json` and, for a kept one, `check.json` with the lab's own sample.

`"exhibit": { "slug": "...", "exhibit": { ... } }`. See [EXHIBITS.md](EXHIBITS.md) for the contract, the pull request and how the room reads them. Exhibit pull requests cost no model or compute money beyond AI-Agent's CI.

## Lab proposals

`"lab_proposal": { "title": "...", "summary": "...", "files": [ { "path", "content" } ] }`, 1 to 3 whole files under `src/`, `api/`, `docs/`, `tests/` or `modal/`. Workflows, hidden paths, environment files, dependency manifests, build and deployment configuration and `schema.sql` are refused. When the Reviewer approves, the lab opens a pull request to the Observable-Lab repository on branch `model-proposal/epoch-<n>-<slug>`, labelled `model-proposal`, with the model as commit author. **The lab never merges these.** Its client for that repository has no merge path at all; the owner reviews and merges by hand. [SECURITY.md](../SECURITY.md) explains why.

The token is `LAB_PROPOSALS_GITHUB_TOKEN`, a fine-grained token for that one repository with **Pull requests: read and write** and **Contents: read and write** and nothing else. It never falls back to another token. `LAB_PROPOSALS_GITHUB_OWNER` names the owner; `LAB_PROPOSALS_GITHUB_REPO` defaults to `Observable-Lab`.

## Spend

Before a tool runs, the server checks its daily limit and today's spend. A Sprite session, GPU job or weights fetch is refused when today's spend plus its worst case (240 s of Sprite time, 210 s of GPU time, or 960 s of fetch time) would pass `LAB_DAILY_BUDGET_USD`. Afterwards its estimated cost is written to the `model_calls` ledger as model `tool/sprite_session`, `tool/gpu_job` or `tool/weights` with `cost_source` `estimate`, so the daily cap, the cron's pause and the epoch's `cost_usd` all include it.

A request for a public dataset is checked the same way against its worst case (960 s of fetch time) and written as `tool/datasets`; the reading of rows for a training run is written as `tool/dataset_rows`.

Tinker is counted differently, because Tinker reports no cost per call: a training run, a call to a trained adapter and a visitor chat message each have the most they could cost set aside first, under their own daily caps, and are then written to the ledger as token counts at Tinker's published prices (`tool/tinker_train`, or the adapter's `lab/<name>`), again with `cost_source` `estimate`. [Tinker training](#tinker-training) has the detail.

## The record

`tool_runs` is created at runtime: `experiment_id`, `epoch`, `model`, `tool`, `request_summary`, `status` (`ok`, `failed`, `error`, `timeout`, `skipped`, `opened`, `merged`, `closed`), `exit_code`, `duration_ms`, `cost_usd`, `output_tail` (cleaned, at most 4 KB), `detail` (small JSON: commands, slug, pull request URL) and `created_at`. `GET /api/experiment` returns the 12 most recent for the current experiment as `tool_runs`, cleaned again on the way out, and the switched-on tools as `tools_enabled`. `tools_enabled` also lists `live_model` while Sprite sessions come with the lab model endpoint, and `live_trained` while that endpoint also answers for trained adapters. A Tinker training run has a second, fuller row in `tinker_runs`, and the money set aside and spent on Tinker per UTC day is in `tinker_spend_days`. Naming and keeping add to the database only once one of them is used: two columns on `tinker_runs` (`display_name`, and `name_key` with its unique index) and the table `tinker_keeps` (`slot`, `slug`, `status`, `kept_by`, `reason`, `experiment_id`, `epoch`, the runner's `job_id` and `call_id`, `requested_at`, `kept_at`, `detail`). A lab that never switches them on never has them. Training on rows of a public dataset adds one column to `tinker_runs`, `dataset_source`, the first time such a run is opened.
